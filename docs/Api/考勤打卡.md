# 考勤打卡

本文档对应 `app/Api/Controllers/AttendanceController.php` 与 `app/Services/AttendanceService.php` 当前实现。

## 路由总览

当前 `routes/api.php` 中已注册的考勤接口如下：

| 方法 | URI | 控制器方法 | 说明 |
| --- | --- | --- | --- |
| `GET` | `/api/attendance/today` | `today` | 今日考勤概览 |
| `GET` | `/api/attendance/records` | `records` | 月度考勤记录 |
| `GET` | `/api/attendance/records/{date}` | `show` | 单日考勤详情 |
| `GET` | `/api/attendance/statistics` | `statistics` | 月度统计 |
| `POST` | `/api/attendance/clock` | `clock` | 考勤打卡 |

> `AttendanceController::index()` 当前仍为预留方法，`routes/api.php` 中**未注册路由**。

---

## 通用说明

- 鉴权：除非特别说明，以下接口均需要 `Authorization: Bearer {access_token}`
- 时间格式：
  - 月份参数使用 `YYYY-MM`
  - 日期参数使用 `YYYY-MM-DD`
  - 响应时间字段使用 `Y-m-d H:i:s`
- 默认月份：`records`、`statistics` 未传 `month` 时，默认按**当前月份**查询

## 考勤打卡

- 方法：`POST`
- URI：`/api/attendance/clock`

### 请求体（JSON）

| 参数 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `clock_method` | int | 否 | 打卡方式，见下方字典。默认 `1` |
| `timezone` | string | 否 | 时区，如 `Asia/Shanghai` |
| `device_id` | string | 否 | 设备ID |
| `device_name` | string | 否 | 设备名称 |
| `lng` | number | 否 | 经度，范围 `-180 ~ 180` |
| `lat` | number | 否 | 纬度，范围 `-90 ~ 90` |
| `address` | string | 否 | 打卡地址 |
| `location_accuracy` | int | 否 | 定位精度（米） |
| `wifi_ssid` | string | 否 | WiFi 名称 |
| `wifi_bssid` | string | 否 | WiFi BSSID |
| `remark` | string | 否 | 备注 |
| `idempotency_key` | string | 否 | 幂等键（建议每次真实打卡动作生成一个 UUID） |

### 业务限制

- 为避免误操作，上班卡与下班卡之间至少间隔 `5` 分钟。

### 请求示例

```json
{
  "clock_method": 1,
  "timezone": "Asia/Shanghai",
  "device_id": "ios-abcdef123456",
  "device_name": "iPhone 16",
  "lng": 121.4737,
  "lat": 31.2304,
  "address": "上海市黄浦区...",
  "location_accuracy": 15,
  "wifi_ssid": "Office-WiFi",
  "wifi_bssid": "00:11:22:33:44:55",
  "remark": "正常到岗",
  "idempotency_key": "1b832f7b-83b8-4d4c-847f-7d2ac7d5b4ba"
}
```

### 响应体

| 参数 | 类型 | 说明 |
| --- | --- | --- |
| `idempotent` | bool | 是否命中幂等返回（`true` 表示本次直接返回首次结果） |
| `clock_log_id` | int | 打卡日志ID |
| `punch_type` | int | 打卡类型，见下方字典 |
| `punch_type_label` | string\|null | 打卡类型文案 |
| `clocked_at` | string | 本次打卡时间 |
| `schedule` | object | 对应日程汇总结果 |

### 响应示例

```json
{
  "code": 200,
  "data": {
    "idempotent": false,
    "clock_log_id": 1024,
    "punch_type": 1,
    "punch_type_label": "上班卡",
    "clocked_at": "2026-05-21 09:03:12",
    "schedule": {
      "id": 889,
      "date": "2026-05-21",
      "status": 4,
      "status_label": "缺卡",
      "actual_start_time": "2026-05-21 09:03:12",
      "actual_end_time": null,
      "actual_work_hours": 0,
      "late_mins": 0,
      "early_leave_mins": 0,
      "absence_mins": 0
    }
  },
  "meta": {
    "timestamp": 1777435057.21,
    "response_time": 0.03
  }
}
```

### 失败场景

当当前时间未匹配到考勤排班时，服务层会抛出业务异常。当前控制器方法未单独捕获该异常，因此实际响应格式依赖全局异常处理。

若第二次打卡距离上班卡不足 5 分钟，接口返回 `422`，示例：

```json
{
  "code": 422,
  "message": "上班卡与下班卡至少间隔 5 分钟，请稍后再试。"
}
```

## 幂等说明（`idempotency_key`）

`idempotency_key` 不是“跨天班”专用字段。

它的作用是：

- 同一个打卡动作因为网络重试、用户重复点击等原因被重复提交时，服务端只认第一次。
- 后续携带同一个 `idempotency_key` 的请求，直接返回第一次的结果，不再重复写入日志和重复计算。

典型做法：

- 前端每次点击“打卡”先生成一个 UUID 作为 `idempotency_key`。
- 如果请求失败重试，继续用这个 UUID。
- 下一次真正新的打卡动作，再换一个新的 UUID。
